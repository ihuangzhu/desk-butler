# DeskButler V1 状态一致性修复设计

## 背景与目标

DeskButler V1 的完整 Release 流水线已经能够构建、测试、发布并生成安装器，但最终范围复审发现五个未被现有测试充分约束的状态一致性缺口：连续失败保护原因没有呈现在恢复卡、登录启动补偿不完整、模块事件异常可能污染生命周期结果、恢复卡异步重入可能混用快照，以及登录启动设置可能覆盖并发设置修改。

本修复只关闭这五个缺口，不增加 AI、远程控制、动态插件、云同步或新的恢复等级。成功标准是：用户看到的状态与实际状态一致；并发操作不会丢失已经提交的设置；观察者失败不能改变业务操作的真实结果；所有异常路径都有确定、可测试的结果。

## 设计原则

1. 每个共享状态只有一个写入协调边界。
2. 一次 UI 操作涉及的读取、决策和发布构成一个不可交错的逻辑事务。
3. 补偿步骤彼此独立尝试，不能因为前一个补偿失败而跳过后一个。
4. 业务生命周期结果优先于观察事件；观察者异常不得重写模块真实状态或覆盖原始异常。
5. 连续失败保护只影响默认选择，不放宽 elevated、非法路径、排除项等既有安全限制。

## 1. 恢复卡快照事务与保护原因

### 状态边界

`RecoveryCardViewModel` 的同一个异步门同时保护：

- `ShowAsync` 加载失败历史并发布新的 `scene`、`Items` 和显示代次；
- 立即恢复、安全恢复、跳过、永久排除等读取当前 `scene`/`Items` 的动作；
- 倒计时只按显示代次隐藏，不取得业务动作所有权。

`ShowAsync` 开始时先取得单调递增的请求代次，再在局部变量中完成失败历史读取和项目 ViewModel 构造，取得门后仅在自己的代次仍是最新请求时一次性替换 `scene` 与 `Items`。这样较慢的旧快照加载既不能留下“新 scene + 旧 Items”或相反组合，也不能在较新的调用已经发布后把界面倒退到旧快照。旧倒计时继续由同一显示代次取消机制隔离。

恢复动作取得同一门后，从同一个已发布状态复制场景和选择列表，再发送恢复命令。动作完成前新的卡片显示不能替换它使用的现场。现有 `AsyncCommand` 防重复不能代替这个跨命令共享门。

### 用户可见保护原因

`RecoveryCardItemViewModel.ProtectionReason` 绑定到项目标题下方。无保护原因时不占布局空间；连续失败达到三次时显示“连续失败 3 次，已默认取消；可手动重新勾选重试”。该提示只解释默认取消，不暗示其他不安全项可以被覆盖。

### 验收

- 并发显示两个快照时，最终 `scene` 和 `Items` 必须来自最后发起的 `ShowAsync`，且二者属于同一快照。
- 恢复动作与新的 `ShowAsync` 交错时，发出的命令必须包含动作开始时同一快照的选择。
- 保护原因在 XAML 中可见并由无障碍树读取；普通项目不显示占位提示。

## 2. 统一设置协调器

### 单一写入入口

`SettingsCoordinator` 是运行期设置的唯一读改写协调器。捕获开关、永久排除和登录启动都通过它执行“取得门—重新读取最新设置—只修改目标字段—保存”的流程。任何命令处理器不得在协调器外保存一份旧的完整设置后再覆盖写回。

协调器提供聚焦的修改操作，而不是暴露任意委托给 UI：

- 设置 `CaptureEnabled`；
- 添加永久排除路径；
- 设置 `StartupEnabled`，并协调外部 `IStartupRegistration`。

每次修改都以门内重新加载的最新设置为基线，因此在登录启动操作等待注册表时，其他设置修改要么先完成并被新基线吸收，要么在它完成后基于其结果继续，不会丢字段。

### 登录启动的提交与补偿

登录启动同时涉及 `settings.json` 与 HKCU Run。操作在设置门内按以下顺序执行：

1. 读取旧设置和旧注册状态；
2. 应用目标注册状态；
3. 保存只改变 `StartupEnabled` 的新设置；
4. 两步都成功后发布新 UI 状态。

若注册操作失败，设置尚未改变，直接返回失败。若设置保存失败，必须独立尝试恢复注册状态和恢复旧设置；两个补偿都要执行，即使其中一个失败。最终错误保留原始保存异常，并附加每个补偿异常，不能用最后一个异常覆盖根因。UI 恢复为协调器重新读取并核实的实际状态；若无法证明一致，则显示失败并保持开关禁用，提示用户从故障信息中处理，不能伪装成功。

### 生命周期

`SettingsCoordinator` 由 `CompositionRoot` 创建一份并注入所有设置命令处理器，随组合根释放。不得为登录启动另建协调器或直接注入裸 `ISettingsStore` 执行读改写。

### 验收

- 捕获、排除和登录启动并发时，各自字段都保留最终提交值。
- 启用、禁用成功时 JSON、注册表和 UI 一致。
- 设置保存失败时，即使 JSON 回滚失败也仍尝试注册表回滚；反向同理。
- 错误结果包含原始失败与全部补偿失败，不发生异常覆盖。

## 3. 模块生命周期与观察事件隔离

### 生命周期结果

`ModuleHost` 对每个模块明确分开三件事：执行生命周期操作、记录真实结果、尽力发布观察事件。

- `StartAsync` 成功后，模块真实状态为 Running；发布 Running 事件失败只记录/聚合为观察故障，不得发布 Failed，也不得把模块当作启动失败。
- `StartAsync` 失败时，必须保留并重新抛出原始启动异常；随后尽力发布 Failed。Failed 事件发布失败只能作为附加诊断，不能覆盖原异常。
- `StopAsync` 使用同样规则：生命周期异常保持为主异常，状态事件是次级观察结果。

V1 不因为事件订阅者失败而中止已经成功的模块生命周期。为避免静默丢失，`ModuleHost` 接受一个 `Action<Exception>` 诊断错误接收器：事件发布失败时把异常交给它，然后按真实生命周期结果继续。诊断接收器自身抛出的异常必须被吞掉，因为它是最后一道观察边界，不能再次污染模块结果。生产组合根把它接到既有结构化诊断日志，不新增遥测子系统。

### 事件总线边界

`InProcessEventBus` 继续负责逐个调用订阅者。ModuleHost 不假设事件发布永远成功，也不把观察事件放进生命周期操作的同一个 `try/catch`。模块页面仍从同一生产事件总线获取状态。

### 验收

- 模块启动成功但 Running 订阅者抛错：模块不被误报 Failed，`StartAsync` 正常返回，诊断接收器收到观察异常。
- 模块启动失败且 Failed 订阅者也抛错：调用者收到原始启动异常，诊断接收器收到事件发布异常。
- 正常启动、停止和状态绑定行为不回归。

## 4. 错误处理与线程规则

- 所有 UI 集合和属性更新回到 WPF Dispatcher 所在线程；协调器本身不持有 Dispatcher。
- `SemaphoreSlim` 的所有等待使用 `try/finally` 释放；释放和取消不会被错误路径跳过。
- 设置门内不显示对话框、不调用 UI 回调，避免持门等待用户操作。
- 恢复卡动作门只覆盖状态快照和业务命令生命周期，不与 15 秒计时器形成相互等待。
- 聚合异常不得包含注册表路径、完整用户数据或其他新增敏感字段。

## 5. 测试策略

每项行为都严格执行 RED → GREEN，并在报告中保存命令、失败原因和通过结果。

### 恢复卡

- 可控延迟的失败历史存储让旧 `ShowAsync` 晚于新调用返回，验证最终状态不混用。
- 在恢复命令阻塞时调用 `ShowAsync`，验证发送的 scene ID 与 item ID 属于同一已发布快照。
- XAML/绑定测试验证 `ProtectionReason` 可见、为空时折叠。

### 设置协调

- 用可控 barrier 同时发起捕获、排除和登录启动修改，验证无字段丢失。
- 覆盖启用、禁用、注册失败、保存失败、JSON 补偿失败、注册补偿失败和双补偿失败。
- 测试明确断言两个补偿都被调用，并检查原始异常未被覆盖。

### 模块生命周期

- Running 订阅失败、Failed 订阅失败、启动与事件同时失败、停止与事件同时失败。
- 生产 CompositionRoot 使用同一个事件总线驱动模块 ViewModel 的既有证据保持通过。

### 回归门禁

- 相关聚焦测试在 Debug 与 Release 下通过。
- 完整 `scripts\verify-release.cmd` 通过：Release 构建零警告零错误，全部非外部门禁测试无失败，publish、Inno Setup 和 SHA-256 成功。
- `git diff --check`、仓库状态、remote 和敏感数据/构建产物扫描通过。
- 不运行安装、卸载、重启、注销、关机或真实用户数据删除。

## 6. 文档与发布状态

用户指南补充连续失败保护提示和设置失败时的真实状态说明。兼容性文档继续把 Windows 11、干净账户、真实重启、诊断 ZIP UI 和产品签名保留为未通过门禁。

这五项修复通过独立范围审查之前，DeskButler 仍只能称为本地 release candidate，不能进入真实重启验收或正式发布。
