# DeskButler 常驻应用设计规格

## 1. 目标

DeskButler 增加“常驻应用”能力，使 QQ、微信、富途牛牛等缩到通知区域或没有普通可见主窗口的第三方应用，也能像工作现场中的窗口一样被用户发现和管理。

常驻应用与最近三份现场快照相互独立：它们在当前 Windows 用户登录后由 DeskButler 自动启动一次，不因切换或裁剪现场而消失；用户主动退出应用后，即使 DeskButler 在同一 Windows 登录会话内重启，也不得再次自动拉起。用户显式点击“立即启动已启用项”不受此限制。

## 2. 已确认的产品行为

- 用户主动点击“保存当前现场”时，同时发现可能需要常驻的第三方应用。
- 后台自动快照、会话结束快照和安全检查点不得新增常驻应用候选。
- 新候选显示给用户确认；高可信候选默认勾选，低可信或启动入口不明确的候选默认不勾选。未经确认不得写入设置。
- 已确认应用进入全局常驻列表，而不是某一份现场的条目。
- 每个 Windows 登录会话只运行一次自动启动批次；DeskButler 登录启动后等待 5 秒，再按列表顺序逐个启动，相邻应用启动间隔 1 秒。
- 已经运行的应用跳过，不启动重复实例。
- 单项失败只记录诊断并继续后续项目，不阻断 DeskButler、窗口捕获或现场恢复。
- 用户主动退出后不重启；本阶段不实现崩溃守护或持续进程监控。
- 每个常驻应用均可启用、禁用、删除，并可人工修正可执行文件路径。

## 3. 平台边界与发现策略

Windows 的公开 `Shell_NotifyIcon` 接口允许应用管理自己的通知区域图标，但没有提供可靠的系统级第三方图标枚举接口。实现不得依赖读取 Explorer 私有工具栏内存、跨进程 `TB_GETBUTTON` 布局或特定 Windows 构建的通知区域内部结构。

因此，产品文案使用“候选常驻应用”，而不是声称完整枚举全部托盘图标。发现边界如下：

1. 枚举当前登录会话中仍存活的进程。
2. 读取可执行文件绝对路径、文件版本信息中的产品/厂商名称、图标和该进程拥有的顶层窗口分类；不读取命令行、账号、窗口内容或应用数据。
3. 优先使用已安装程序目录及产品/厂商名称把同一产品的主进程、渲染进程、更新器和崩溃上报进程折叠为一个候选组；信息不足时才按正规化可执行路径单独成组。
4. 排除：
   - DeskButler 自身；
   - 其他 Windows 会话和 Session 0；
   - 无法读取可执行路径或疑似提升权限的进程；
   - Windows 系统目录、临时目录和安装器缓存中的程序；
   - 已作为普通窗口收入本次现场的可执行路径；
   - 已存在于常驻列表的路径。
5. 其余“当前正在运行但没有普通可见主窗口”的第三方程序成为候选，并分级：
   - 高可信：拥有隐藏、工具型或 DWM cloaked 顶层窗口，且能匹配已安装产品或稳定产品信息；默认勾选；
   - 低可信：完全没有窗口、缺少稳定产品信息，或名称疑似 helper、updater、crash reporter、虚拟机辅助工具；显示但默认不勾选。

候选组默认选择最可能的主程序作为启动入口：依次优先通知区域风格隐藏窗口的所有者、已安装程序的 `DisplayIcon`/安装入口、产品根目录中的主程序。无法可靠选择时不得猜测，候选保持未勾选并要求用户浏览指定 `.exe`。组内其他可执行路径只作为“运行中识别路径”折叠显示。

发现是帮助用户缩小范围的安全筛选，不是无提示自动授权。错误识别由确认界面和路径修正入口兜底。

## 4. 数据模型与兼容性

Core 设置增加全局 `ResidentApplicationsEnabled` 布尔值，首次升级默认 `true`。同时增加不可变的常驻应用条目，稳定字段为：

- `LaunchPath`：实际启动入口的绝对 `.exe` 路径；
- `KnownProcessPaths`：判断产品是否已运行的一组绝对 `.exe` 路径，必须包含 `LaunchPath`；
- `DisplayName`：用户可读名称；
- `Enabled`：是否参与登录启动；
- `LaunchOrder`：非负整数顺序。

应用身份是经过 `Path.GetFullPath`、去除非根尾分隔符并按 Windows 大小写不敏感语义比较的 `LaunchPath`。同一启动入口只能存在一项；任何已知运行路径也不得同时属于两个已启用条目。图标从当前文件实时派生，不写入 JSON。

`ButlerSettings` 增加 `ResidentApplicationsEnabled` 和 `ResidentApplications`。`SettingsDocument` 对缺失的总开关使用 `true`，对缺失或 `null` 的列表安全降级为空列表，因此升级前的 `settings.json` 无需显式迁移。加载时逐项正规化并隔离畸形、重复或空路径条目：按 JSON 顺序保留第一个有效启动入口；后续条目若与其启动入口重复则忽略，若只发生运行识别路径冲突则保留条目但移除冲突识别路径，并写诊断。任何条目的 `LaunchPath` 被冲突移除时该条目无效。不能因为一个常驻应用路径损坏而把捕获、排除等其他设置回退到默认值。

新增、删除、启用、禁用、改路径和排序全部通过现有共享 `SettingsCoordinator` 串行提交，不能绕过捕获、排除和登录启动设置的统一事务门。

## 5. 手动保存与确认流程

普通窗口现场保存继续由 `CaptureCoordinator` 负责；常驻发现不得侵入自动捕获模块。

用户主动保存时，即使捕获已暂停、窗口没有变化、没有普通窗口或本次没有写入新快照，也必须继续执行常驻候选发现。手动协调边界返回明确结果：窗口现场是否实际写入、未写入原因、普通窗口可执行路径集合、候选发现结果。自动调度器继续通过忽略结果的适配器使用原捕获流程。

手动保存工作流按以下顺序执行：

1. 发送现有手动现场保存命令。
2. 使用本次普通窗口候选的可执行路径集合，运行常驻候选发现。
3. 排除已有常驻项后，把候选及单调递增的发现代次原子发布到主界面待确认集合。
4. 没有候选时，仅显示“现场已保存”。
5. 有候选时，显示“发现 N 个可能需要常驻的应用”，并按候选可信度设置默认勾选状态。
6. 用户点击确认时先捕获当前发现代次；取得设置事务门后必须再次核实代次和候选对象身份。过期确认是无副作用 no-op；有效确认一次性写入全部勾选项。未勾选项本次不写入，下次主动保存仍可再次出现。

新一轮发现替换尚未确认的旧候选，而不是合并两个时刻的进程状态。确认、忽略和新发现遵守 latest-wins；设置失败不得清空同代次待确认集合。

从主窗口保存时，确认区显示在首页保存按钮下方。从托盘选择“保存当前现场”时复用同一工作流；若发现候选，则打开主窗口并聚焦确认区。后台自动保存永远不打开窗口。

确认区每项显示图标、显示名称和完整 `.exe` 路径。提供“确认添加”和“本次忽略”。“本次忽略”只清空待确认集合，不建立永久排除规则。

## 6. 设置页

设置页新增“常驻应用”区域：

- 总开关绑定 `ResidentApplicationsEnabled`，允许或暂停全部常驻应用的登录启动；
- 每项启用开关；
- 显示名称、路径和缺失/无法访问状态；
- 上移、下移调整启动顺序；
- 浏览选择 `.exe` 以修正路径；
- 删除条目；
- “从正在运行的程序中查找”入口，复用手动保存的候选发现但不保存现场；
- “浏览添加”入口，允许直接选择 `.exe`。

人工选择路径时必须显示最终绝对路径。只允许本地固定磁盘上的普通 `.exe` 文件；UNC、网络共享、可移动盘、Windows 系统目录、临时目录、安装器缓存和当前无法访问的路径默认拒绝。需要提升权限的候选默认不允许自动启用。应用文件后来丢失时保留设置并显示警告，避免路径短暂不可用导致用户配置消失。

自动更新导致 `LaunchPath` 失效时，可用同产品/厂商及安装目录信息显示“发现可能的新路径”，但必须由用户确认后才能替换启动入口和运行识别路径，不能静默改写持久化配置。

## 7. 登录启动执行

新增独立的常驻应用启动协调器，由组合根拥有和清理。它不属于工作区恢复模块，也不改变最近现场的恢复结果。

启动协议：

1. DeskButler 主对象图和托盘启动成功后，建立可取消的后台启动任务，并读取当前进程令牌的 Authentication LUID 作为 Windows 登录会话身份。
2. 使用可测试时钟等待 5 秒。
3. 读取会话记录：同一 LUID 的批次已经完成则结束；存在未完成计划则准备续跑；不存在当前 LUID 记录则重新加载最新设置并原子建立固定计划。`ResidentApplicationsEnabled` 关闭时建立已完成的空计划后结束。
4. 新计划按 `LaunchOrder`、路径稳定排序启用项；续跑严格保持会话文件中的原计划顺序，并用最新设置解析对应条目。
5. 每项启动前枚举当前会话进程，并用该项全部 `KnownProcessPaths` 按正规化路径判断是否已经运行。
6. 已运行则记录“跳过”；无法可靠核实是否运行时也跳过，优先避免重复实例。
7. 验证路径仍是本地固定磁盘上的普通文件且不在禁止目录后，使用 `LaunchPath` 启动，不携带捕获命令行或账号参数，也不请求 `runas`。
8. 记录成功或脱敏失败诊断；继续下一项前等待 1 秒。
9. DeskButler 退出时取消尚未开始的等待和后续启动，不终止已经启动的第三方应用。

`%LOCALAPPDATA%\DeskButler\resident-launch-session.json` 保存格式版本、Authentication LUID、本登录会话首次批次确定的固定启动计划、各项已尝试状态和批次完成状态。首次协调时从当时的设置原子建立计划；总开关关闭时建立已完成的空计划。此后在同一 Authentication LUID 下，设置中新增、启用、删除或改序都不改变该计划，因而只能通过“立即启动”影响当前会话，自动生效要等下次 Windows 登录。

每项自动启动前先原子登记为“本登录会话已尝试”，再调用外部进程边界；DeskButler 崩溃或重启后只继续固定计划中尚未尝试的项目，不重复拉起用户已经退出的项目。所有计划项处理后原子标记批次完成，同一 LUID 不得新建第二批。新的 Authentication LUID 自动建立新批次；旧会话记录可被原子替换。续跑时仍从最新设置读取对应条目的路径和启用状态：已经删除或禁用的计划项标记为跳过，不能按会话文件中的旧路径启动。

“立即启动已启用项”是显式用户操作，不受自动批次记录限制，但仍必须 single-flight、检查 `KnownProcessPaths` 并避免重复实例。修改设置不会自动启动或停止当前应用。

DeskButler 不为任何第三方应用创建独立的 `Run` 注册表值、计划任务、服务或快捷方式；只有 DeskButler 自身保留现有登录启动注册。

## 8. 错误处理与诊断

- 候选枚举中的单进程退出、访问拒绝和路径失效只跳过该进程。
- 系统级枚举失败显示可理解的“常驻应用发现失败”，不得撤销已经成功保存的窗口现场。
- 设置确认失败不丢失待确认集合，允许重试。
- 过期候选确认、忽略或路径修正不得改变新一代候选或设置。
- 启动失败不得阻断其他常驻应用或 DeskButler 启动。
- 诊断记录只包含显示名称、脱敏后的可执行路径、结果类别和错误类型；不记录命令行、账号、令牌或窗口内容。
- 文件不存在、访问拒绝、已运行、启动成功和启动失败使用不同结果类别，方便虚拟机验收定位。
- `resident-launch-session.json` 使用原子替换；畸形文件先重命名为带时间戳的故障证据，再为当前 Authentication LUID 原子写入“已完成的空计划”。本次登录不自动启动，DeskButler 重启也不会重试；下一个新 LUID 可正常建立新批次。

## 9. 模块边界

- Core：常驻应用总开关、条目模型、路径身份规则和平台无关接口。
- Infrastructure.Windows：当前会话进程发现、路径/系统目录判定、运行中检查和进程启动。
- Desktop.Hosting：手动保存后发现、设置事务命令、登录启动协调和组合根 wiring。
- Desktop.ViewModels / Views：候选确认区与设置页管理。
- WorkspaceRecovery：保持窗口快照和恢复职责，不读取或启动常驻列表。

常驻应用启动失败不得改变模块生命周期状态；窗口恢复失败历史也不得混入常驻应用启动结果。

## 10. 测试策略

所有行为按 TDD 实现，不使用固定睡眠等待。

### 单元与集成测试

- JSON 旧设置缺失新字段时加载空列表；新字段往返保持路径、启用和顺序。
- 畸形或重复单项被隔离，其他设置不回退默认值。
- 全局开关默认值、持久化、并发切换和启动短路均有测试。
- 发现器按会话、磁盘类型、系统/临时目录、权限、已有窗口和已有常驻项逐项过滤。
- 同产品多进程折叠为一组；高可信默认选中，低可信默认不选；主入口不明确时不猜测。
- 自动快照、会话结束快照不调用常驻发现；两个手动入口调用一次；捕获暂停、无窗口和现场未变化仍运行发现。
- 候选代次 latest-wins；过期确认 no-op；确认一次性写入；本次忽略不写入；保存成功但发现失败仍保留现场。
- 常驻设置与捕获、排除、DeskButler 登录启动开关并发修改时不丢字段。
- 5 秒延迟、1 秒间隔使用假时钟确定性验证。
- `LaunchPath` 与 `KnownProcessPaths` 的启动/去重语义分别覆盖；已运行、无法核实、路径缺失、单项启动失败和取消退出分支均有测试。
- 相同 Authentication LUID 下固定计划、崩溃续跑、完成后重启、设置中途变化均不产生第二批；新 LUID 建立新批次；会话文件原子写入及损坏后的空计划降级有测试。
- 两个并发“立即启动”调用共享一个执行批次，避免重复进程。
- 组合根部分构造/启动失败时，常驻启动协调器按现有 exactly-once 清理协议释放。

### Windows 10 虚拟机验收

1. 建立纯净快照并安装 DeskButler。
2. 启动 QQ、微信、富途，缩到通知区域。
3. 主动保存现场，确认三者作为候选出现且默认勾选。
4. 确认后重启虚拟机，验证 DeskButler 约 5 秒后依序启动三者。
5. 保持其中一个已经运行，再次执行“立即启动”，验证 `KnownProcessPaths` 不产生重复实例。
6. 主动退出微信并重启 DeskButler，验证同一 Windows 登录会话内不会被再次自动拉起。
7. 禁用、改路径、删除条目并重启，逐项验证。
8. 卸载 DeskButler，确认不终止第三方应用；按卸载数据选项验证设置保留或删除。

## 11. 文档、隐私与卸载

- `docs/privacy.md` 增加 `ResidentApplicationsEnabled`、常驻应用名称/路径/运行识别路径、`resident-launch-session.json` 及诊断类别说明。
- `docs/user-guide.md` 说明主动保存发现、可信度默认值、设置管理、登录启动一次和手动立即启动。
- `docs/troubleshooting.md` 说明候选漏检、辅助进程误识别、路径更新、权限、重复实例和会话记录损坏处理。
- README 与 Windows 10/11 手工清单同步功能边界和验收步骤。
- 常驻设置随 `settings.json` 保留；普通卸载不删除。只有用户在卸载时选择“同时删除设置、快照和日志”或静默卸载显式传入 `/DELETEUSERDATA=1`，才删除常驻列表和会话记录。
- 卸载 DeskButler 不终止、注销或修改任何已经启动的第三方应用，也不需要额外清理第三方启动注册，因为本功能从不创建它们。

## 12. 非目标

本阶段不实现：

- 读取 Explorer 私有通知区域结构；
- 自动枚举 100% 的托盘图标；
- 捕获或恢复第三方程序内部登录状态、账号、聊天、行情布局或交易状态；
- 保存命令行参数；
- 应用崩溃或主动退出后的持续拉起；
- 结束、重启或升级第三方应用；
- 跨 Windows 用户同步常驻列表；
- 远程指令、AI 管家或动画形象。

## 13. 完成标准

- QQ、微信和富途在 Windows 10 虚拟机中缩到通知区域后，可通过主动保存流程发现、确认并加入常驻列表。
- 登录后按设计只自动启动一次，DeskButler 在同一 Authentication LUID 下重启也不重复；已有任一已知产品进程时不启动，用户主动退出后不自动拉起。
- 常驻应用不依赖最近三份现场，不影响窗口捕获与恢复。
- 旧设置兼容、总开关持久化、候选代次一致、并发设置不丢失、退出清理 exactly-once。
- 自动测试、Release 构建、安装包生成和虚拟机验收清单通过；任何真实重启仍需用户在执行前即时确认。
